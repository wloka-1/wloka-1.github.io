Where I match

"Own and evolve our design system, bringing today's fragmented systems and patterns into a strong, shared foundation."

I've started one from zero and I've had to fix fragmentation twice.

At Qualcomm there was no system and three brands with no shared language. I set the visual direction, wrote the principles the rest of the team built from, defined the taxonomy, and owned iconography and the documentation architecture. I ran original research to settle which patterns the system would ship, then got buy-in from the Heads of Design before the roadmap was committed.

At BNY the problem is the opposite. Systems already existed, built in isolation, inside a bank where governance is not optional. Cohesion there is a negotiation, not a decree.

Qualcomm case study

"Create tools and ways of working that enable others."

The enablement work is the part I like most.

  • Built an automated design audit that screenshots inconsistencies across the system and files them as issue-tracker entries. The team gets the QA without doing the QA.
  • Built an AI-in-the-loop documentation pipeline at Qualcomm that cut writing effort 120x and CMS page creation 95%, which is how 60+ component docs shipped on schedule for an enterprise beta.
  • Wrote the governance and contribution model for a distributed team across several time zones, because a system nobody can contribute to stops being a system.

"We're also excited about what design enablement can look like in an AI-oriented world."

This is the part I have a real position on.

A design system is deterministic. A model is not. So the system's job is no longer documentation people are asked to read. It's the set of rules the generator has to obey, enforced in code.

That means instructions written to be read by whatever agent is doing the building, with lint, tests, and deterministic checks that catch drift and fix it. Documentation for humans becomes a side effect rather than the artifact. It is nowhere near solved, which is exactly why it needs a designer writing it: whoever decides what is allowed is more load-bearing than before, not less.

I work this way myself. Prototypes get built with Claude against the same code context and version as production, so most of what I build goes to production rather than to a handoff doc. Five prototype iterations in a single session, design-to-engineer-ready in hours.

What I'd ask first

Before touching components, I'd want to know three things, because the answers decide the whole sequence:

  • Which of the fragmented systems are actually load-bearing in production, and which are just still open in someone's file?
  • Where does brand end and product begin in your tokens, and who currently gets the final call when they disagree?
  • What breaks first when generation scales: consistency, accessibility, or claimant comprehension in the moments that matter most?

That last one is the reason this role is interesting to me. Claims are a stressed, vulnerable, high-consequence moment, and a foundation that carries clarity into that moment is a better problem than a component library.
